# Специфікація вимог до системи (SRS) — Telegram Task Tracker Bot & Mini App

Цей документ визначає повний, несуперечливий, атомарний та тестований перелік вимог до системи.
Кожна вимога відповідає принципам якості вимог та тестування:
1. **Атомарність (Atomic)** — одна неподільна функція або правило на вимогу.
2. **Повна визначеність (Complete)** — описані входи, виходи, дефолтні значення та граничні випадки.
3. **Несуперечливість (Consistent)** — відсутність конфліктів між вимогами та бізнес-правилами.
4. **Однозначність (Unambiguous)** — точні формулювання без суб'єктивних оцінок.
5. **Тестованість (Testable)** — кожна вимога містить формальні критерії прийняття (Acceptance Criteria: Given-When-Then).
6. **Здійсненність (Feasible)** — 100% відповідність обраному стеку (aiogram 3, FastAPI, SQLite WAL, Gemini 2.5 Flash, React TMA).
7. **Простежуваність (Traceable)** — унікальний ID (`REQ-XXX`) та прив'язка до завдань у `_docs/tasks.md`.
8. **Пріоритетність (Prioritized)** — класифікація за методом MoSCoW (Must, Should, Could, Won't).

## 1. Користувачі, ідентифікація та часові пояси

### REQ-USR-01: Реєстрація та онбординг користувача
* **Пріоритет:** Must Have
* **Простежуваність:** Task 3, Task 6
* **Опис:** При відправці команди `/start` у Telegram-боті система перевіряє наявність запису `telegram_id` у таблиці `users`. Якщо користувач новий, створюється запис із дефолтним часовим поясом `Europe/Kyiv`, фіксується час створення, а користувач отримує привітальне повідомлення з інструкцією. Якщо користувач уже існує, оновлюються лише метадані сесії, а існуючі дані не перезаписуються.
* **Критерії прийняття (Acceptance Criteria):**
  - **Given:** Новий користувач викликає команду `/start`.
  - **When:** Бот обробляє команду.
  - **Then:** У базі створюється запис `User(telegram_id=user.id, timezone='Europe/Kyiv')`, а бот надсилає інструкцію з кнопкою відкриття Mini App.
  - **Given:** Існуючий користувач повторно викликає `/start`.
  - **When:** Бот обробляє команду.
  - **Then:** Новий запис не створюється, помилки не виникає, повертається вітання для поверненого користувача.

### REQ-USR-02: Конфігурація індивідуального часового поясу
* **Пріоритет:** Must Have
* **Простежуваність:** Task 3, Task 17
* **Опис:** Користувач може змінити свій часовий пояс через налаштування в боті або в Mini App. Система валідує переданий рядок через `zoneinfo.ZoneInfo`. Якщо ідентифікатор невалідний, система відхиляє зміни та повертає помилку.
* **Критерії прийняття:**
  - **Given:** Користувач надсилає валідний рядок таймзони (наприклад, `Europe/Berlin`).
  - **When:** Запит на зміну таймзони обробляється API або ботом.
  - **Then:** Поле `user.timezone` оновлюється в базі, всі наступні розрахунки локального часу (00:00, 09:00) виконуються за новою таймзоною.
  - **Given:** Користувач надсилає невалідний рядок (наприклад, `Mars/Olympus`).
  - **When:** Валідатор перевіряє значення.
  - **Then:** Зміна відхиляється з HTTP 422 або повідомленням про помилку в чаті, попередній часовий пояс зберігається.

## 2. Модель даних та життєвий цикл завдань

### REQ-TSK-01: Структура сутності завдання
* **Пріоритет:** Must Have
* **Простежуваність:** Task 2, Task 5
* **Опис:** Сутність `Task` містить обов'язкові атрибути: `id` (int, autoincrement), `user_id` (bigint, foreign key до `users.telegram_id`), `title` (string, max 255), `status` (enum: `todo`, `done`, `canceled`), `priority` (enum: `low`, `medium`, `high`), `target_date` (date: YYYY-MM-DD), `created_at` (datetime UTC); та опціональні атрибути: `tag` (string, max 50), `deadline_at` (datetime UTC), `recurrence` (string: `daily` або `weekdays:[0,1,2,3,4,5,6]`), `reminder_sent_1h` (bool, default False), `reminder_sent_10m` (bool, default False).
* **Критерії прийняття:**
  - **Given:** Створюється нове завдання із мінімальним набором полів (`title`, `target_date`).
  - **When:** Запис фіксується в БД.
  - **Then:** `status` за замовчуванням дорівнює `todo`, `priority` — `medium`, `created_at` автоматично виставляється в UTC, `reminder_sent_*` дорівнюють `False`.

### REQ-TSK-02: Зміна статусу завдання
* **Пріоритет:** Must Have
* **Простежуваність:** Task 5, Task 10, Task 12
* **Опис:** Завдання може змінювати статус між `todo`, `done` та `canceled`. Зміна статусу доступна лише авторизованому власнику завдання (`task.user_id == current_user.telegram_id`).
* **Критерії прийняття:**
  - **Given:** Завдання перебуває у статусі `todo`.
  - **When:** Користувач-власник клікає чекбокс або надсилає запит PATCH.
  - **Then:** Статус оновлюється на `done`, завдання відображається закресленим у списку.
  - **Given:** Користувач намагається змінити статус завдання іншого користувача.
  - **When:** Запит проходить перевірку прав.
  - **Then:** Система повертає HTTP 403 / 404, стан завдання в БД залишається незмінним.

## 3. Обробка аудіо/тексту та AI-парсинг через Gemini

### REQ-AI-01: Прийом голосових повідомлень Telegram
* **Пріоритет:** Must Have
* **Простежуваність:** Task 4, Task 7
* **Опис:** Бот приймає голосове повідомлення (.ogg Opus), завантажує його байти в пам'ять через Telegram API (без збереження сміттєвих тимчасових файлів на диску) і передає у сервіс розпізнавання.
* **Критерії прийняття:**
  - **Given:** Користувач надсилає голосове повідомлення тривалістю до 120 секунд.
  - **When:** Хендлер aiogram отримує повідомлення.
  - **Then:** Бот відображає індикатор дії `typing` / `record_voice`, завантажує аудіопотік у `io.BytesIO` та викликає AI-парсер.

### REQ-AI-02: Структуроване витягування задач через Gemini 2.5 Flash
* **Пріоритет:** Must Have
* **Простежуваність:** Task 4
* **Опис:** Модель Gemini 2.5 Flash отримує аудіобайти або текст разом із системним промптом, локальним часом користувача та вихідною Pydantic-схемою. Модель повертає список розпізнаних задач із розрахованими абсолютними датами (`target_date`), дедлайнами (`deadline_at` у часовому поясі користувача з конвертацією в UTC), пріоритетом (`low`/`medium`/`high`) та тегом (без решітки, max 50 символів).
* **Критерії прийняття:**
  - **Given:** Користувач диктує: «Завтра о 15:00 здати звіт по роботі, пріоритет високий».
  - **When:** Gemini парсить аудіо з урахуванням `user.timezone`.
  - **Then:** Повертається об'єкт: `title="Здати звіт"`, `target_date=tomorrow`, `deadline_at=tomorrow 15:00:00`, `priority="high"`, `tag="робота"`.
  - **Given:** Аудіо містить незв'язний шум або немає жодної задачі.
  - **When:** Gemini формує результат.
  - **Then:** Повертається порожній список задач, бот чемно повідомляє, що не вдалося розпізнати задачі.

### REQ-AI-03: Інтерактивне підтвердження збереження розпізнаних задач
* **Пріоритет:** Must Have
* **Простежуваність:** Task 7
* **Опис:** Розпізнані задачі НЕ зберігаються в БД автоматично. Бот надсилає форматований список із нумерацією та двома інлайн-кнопками: `[✅ Зберегти]` і `[✏️ Виправити]`. При натисканні `[✅ Зберегти]` задачі пачкою зберігаються в БД, а клавіатура замінюється статусом «Збережено». При натисканні `[✏️ Виправити]` користувачеві пропонується ввести виправлений текст або надиктувати знову.
* **Критерії прийняття:**
  - **Given:** Бот сформував повідомлення з кнопками підтвердження.
  - **When:** Користувач тисне `[✅ Зберегти]`.
  - **Then:** Всі розпізнані задачі додаються до таблиці `tasks` зі статусом `todo`, а повідомлення редагується на «✅ Задачі успішно збережено».
  - **Given:** Інший користувач намагається натиснути інлайн-кнопку в групі або пересланому повідомленні.
  - **When:** Бот перевіряє `callback_query.from_user.id`.
  - **Then:** Дія відхиляється спливаючим алеротом (`answer_callback_query(show_alert=True)`).

## 4. Опівнічне рев'ю ("Хвости" о 00:00) та ранковий пуш (09:00)

### REQ-SCH-01: Розрахунок подій 00:00 за індивідуальною таймзоною
* **Пріоритет:** Must Have
* **Простежуваність:** Task 8, Task 13
* **Опис:** Планувальник щохвилини перевіряє користувачів, для яких поточний локальний час дорівнює `00:00` (вікно перевірки: 00:00:00 - 00:00:59). Для кожного такого користувача виконується пошук невиконаних задач (`status == 'todo'`) за попередній календарний день.
* **Критерії прийняття:**
  - **Given:** У користувача з таймзоною `Europe/Kyiv` настала 00:00, і в нього є 2 невиконані задачі за вчора.
  - **When:** Планувальник запускає тригер.
  - **Then:** Користувач отримує повідомлення «Невиконані задачі за вчора» з інлайн-кнопками `[Перенести на сьогодні]` та `[Закрити]` для кожної задачі, після чого бот пропонує надиктувати план на новий день.
  - **Given:** У користувача немає невиконаних задач о 00:00.
  - **When:** Планувальник запускає тригер.
  - **Then:** Користувач отримує коротке повідомлення «Всі задачі виконано! Запишіть план на сьогодні».
  - **Given:** Тригер уже відпрацював для користувача сьогодні.
  - **When:** Відбувається наступний хвилинний тік.
  - **Then:** Повторне надсилання повідомлення блокується прапорцем ідемпотентності.

### REQ-SCH-02: Ранковий пуш о 09:00 із Mini App кнопкою
* **Пріоритет:** Must Have
* **Простежуваність:** Task 13
* **Опис:** О 09:00 за місцевим часом користувача система формує ранковий дайджест із переліком задач на сьогодні (`target_date == today`, `status == 'todo'`). Повідомлення супроводжується інлайн-кнопкою `WebAppInfo` («Відкрити план»), яка запускає Telegram Mini App.
* **Критерії прийняття:**
  - **Given:** На годиннику користувача 09:00.
  - **When:** Спрацьовує ранкова джоба.
  - **Then:** Користувач отримує пуш із кількістю завдань на день та прямою кнопкою відкриття Mini App.

### REQ-SCH-03: Сповіщення про наближення дедлайнів (-1 год та -10 хв)
* **Пріоритет:** Must Have
* **Простежуваність:** Task 14
* **Опис:** Система щохвилини сканує задачі зі статусом `todo`, у яких заповнено `deadline_at`.
  - Якщо до дедлайну залишилося $\le 60$ хв і `reminder_sent_1h == False`, надсилається нагадування і прапорець ставиться в `True`.
  - Якщо до дедлайну залишилося $\le 10$ хв і `reminder_sent_10m == False`, надсилається нагадування і прапорець ставиться в `True`.
* **Критерії прийняття:**
  - **Given:** Завдання має дедлайн через 55 хвилин, статус `todo`, `reminder_sent_1h == False`.
  - **When:** Працює планувальник дедлайнів.
  - **Then:** Користувачеві приходить повідомлення «⏳ Залишилася 1 година до дедлайну: [Назва задачі]», а в базі `reminder_sent_1h` стає `True`.
  - **Given:** Завдання було виконане (`done`) за 2 години до дедлайну.
  - **When:** Час до дедлайну досягає 60 хвилин.
  - **Then:** Сповіщення не надсилається.

## 5. Telegram Mini App (TMA) та REST API

### REQ-API-01: Автентифікація через Telegram `initData`
* **Пріоритет:** Must Have
* **Простежуваність:** Task 9
* **Опис:** Кожен HTTP-запит від Mini App до бекенду містить заголовок `Authorization: tma <raw_init_data>`. Бекенд валідує HMAC-SHA256 хеш відповідно до офіційної специфікації Telegram. Час створення `auth_date` не повинен перевищувати 86400 секунд (24 години).
* **Критерії прийняття:**
  - **Given:** Запит містить валідний рядок `initData`, підписаний секретним ключем бота.
  - **When:** FastAPI-dependency обробляє запит.
  - **Then:** Запит успішно проходить, ендпоінт отримує поточний `telegram_id`.
  - **Given:** Рядок `initData` підроблено або `hash` не збігається.
  - **When:** FastAPI-dependency валідує підпис.
  - **Then:** Повертається статус HTTP 401 Unauthorized, доступ до даних блокується.

### REQ-API-02: REST-ендпоінти списку та фільтрації завдань
* **Пріоритет:** Must Have
* **Простежуваність:** Task 10
* **Опис:** Бекенд надає ендпоінти:
  - `GET /api/tasks?date=YYYY-MM-DD` — список задач на дату.
  - `POST /api/tasks` — створення задачі.
  - `PATCH /api/tasks/{id}` — оновлення статусу, пріоритету, дедлайну.
  - `DELETE /api/tasks/{id}` — видалення задачі.
  Всі запити ізольовані в межах `user_id` авторизованого користувача.
* **Критерії прийняття:**
  - **Given:** Користувач запитує задачі на сьогодні.
  - **When:** Викликається `GET /api/tasks?date=2026-11-19`.
  - **Then:** Повертається JSON-масив задач користувача за вказану дату, відсортований: спочатку `todo` (за пріоритетом high -> medium -> low), потім `done`.

### REQ-TMA-01: Інтерактивний чекліст Mini App
* **Пріоритет:** Must Have
* **Простежуваність:** Task 11, Task 12
* **Опис:** Головний екран відображає задачі на сьогодні з кольоровими бейджами пріоритетів, тегами, дедлайнами та чекбоксами. При натисканні на чекбокс статус негайно оптимістично перемикається в UI (`done` / `todo`) із закресленням тексту, після чого статус синхронізується з сервером.
* **Критерії прийняття:**
  - **Given:** Користувач відкрив Mini App.
  - **When:** Користувач клікає на незакриту задачу.
  - **Then:** Задача закреслюється, відправляється PATCH-запит. У разі помилки мережі стан повертається назад із візуальним сповіщенням (Toast).

### REQ-TMA-02: Повторювані задачі (Recurrence)
* **Пріоритет:** Should Have
* **Простежуваність:** Task 12
* **Опис:** Користувач може призначити задачі повторюваність: щодня (`daily`) або за днями тижня (наприклад, понеділок, середа, п'ятниця). При переході на новий день планувальник або запит `GET /api/tasks` автоматично генерує екземпляр задачі на поточну дату, якщо вона підпадає під правило повторення.
* **Критерії прийняття:**
  - **Given:** Задача має правило повторення `daily`.
  - **When:** Настає новий календарний день.
  - **Then:** У списку задач на новий день автоматично присутній екземпляр цієї задачі зі статусом `todo`.

### REQ-TMA-03: Календарний перегляд
* **Пріоритет:** Should Have
* **Простежуваність:** Task 15
* **Опис:** Вкладка «Календар» дозволяє вибрати будь-яку дату та переглянути історію виконання або заплановані задачі на майбутнє. Дні з повністю виконаними задачами помічаються зеленим маркером, з частково виконаними — жовтим.
* **Критерії прийняття:**
  - **Given:** Користувач обирає минулу середу в календарі.
  - **When:** Відбувається запит до API.
  - **Then:** Відображається список задач за цю дату зі збереженими на той момент фінальними статусами.

### REQ-TMA-04: Звіти, продуктивність та стріки
* **Пріоритет:** Could Have
* **Простежуваність:** Task 16
* **Опис:** Дашборд показує статистику: графік виконаних задач за останні 7/30 днів (`Recharts`), кругову діаграму розподілу за тегами та лічильник поточного стріку (кількість днів поспіль, коли було виконано щонайменше 1 заплановане завдання).
* **Критерії прийняття:**
  - **Given:** Користувач виконував задачі щодня протягом 5 днів поспіль.
  - **When:** Відкривається вкладка «Дашборд».
  - **Then:** Лічильник показує «Стрік: 🔥 5 днів», графік коректно відображає стовпчики за кожен із днів.

## 6. Нефункціональні вимоги (NFR)

### REQ-NFR-01: База даних та продуктивність SQLite
* **Пріоритет:** Must Have
* **Простежуваність:** Task 2
* **Опис:** SQLite повинна працювати виключно в режимі `PRAGMA journal_mode=WAL` із `PRAGMA busy_timeout=5000` та увімкненими зовнішніми ключами `PRAGMA foreign_keys=ON`. Це гарантує відсутність взаємних блокувань читання/запису між ботом, FastAPI та фоновими джобами.

### REQ-NFR-02: Ізоляція та безпека даних
* **Пріоритет:** Must Have
* **Простежуваність:** Task 9, Task 10
